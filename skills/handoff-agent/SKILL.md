# Handoff Agent · 长对话自动交接术

> 「你的上下文会死，交接文件不会。」——蒸馏自 planning-with-files (26392★)、
> Continuous-Claude-v3 (3931★)、Agent-Skills-for-Context-Engineering (17851★)、
> repo-context-ledger、baton 等开源项目（MIT，见 references/sources.md）。

## 核心理念（心智模型）

### 1. 上下文是 RAM，文件系统是磁盘
对话窗口是易失的、有限的；磁盘是持久的、无限的。
**任何重要的东西都要写进 交接.md**，而不是只留在对话里。
→ 上下文被清空/压缩/切换后，交接文件还在，工作可以无缝继续。

### 2. 交接抓的是"对方无法重建的东西"
交接文件不是聊天记录复述，而是：
- **意图**（为什么要做这件事）
- **已排除的死路**（什么试过不行，省得下个对话重新推导）
- **确切的下一步**（具体到下一个动作）
→ 这三样是下一个对话从代码/文档/历史里**无法自行重建**的。

### 3. 持续记录，而非等压缩（Compound, don't compact）
不要等到上下文满了才写交接。**每完成一个关键节点就追加记录**。
上下文阈值不是"要写交接了"的信号，而是"该切换了"的信号——记录应该早已就绪。

### 4. 验证后再写（先验证，再交接）
交接文件里的"当前状态"必须基于文件系统的真实情况（git status、实际文件、测试结果），
**不能只凭对话记忆**。凭聊天叙事写的交接，比没有交接更糟。

### 5. 预判切换，不做被动受害者
在上下文达到硬上限**之前**主动切换（约 80% 阈值），而不是等到性能明显下降
或被迫压缩时才行动。注意力随上下文增长退化（lost-in-the-middle），
提前切换是保持质量的关键。

## 执行流程

### Phase 0: 会话开始——必做检查

每个对话**开始时**（无论新旧）：
1. 检查项目根目录是否存在 `交接.md`
2. 存在 → **先读它**，从"下一步"开始继续，而不是从头问用户
3. 不存在 → 创建空 `交接.md`（模板见下），填入本次对话的目标

**铁律：对话开始前必须先保证 交接.md 存在并可读。这是新对话接力的唯一入口。**

### Phase 1: 工作中——边对话边记录

对话过程中，以下事件**必须立即**追加/更新 交接.md：
- 明确/修正了目标
- 完成了一个关键步骤（标记完成 + 结果）
- 遇到并解决了阻塞（记录解法）
- 排除了一条无效路径（**高价值**，记入"已排除"）
- 做出重要决策（记录决策 + 理由）
- 发现重要的边界/约束/坑

记录用追加式（append），保留时间线，不要覆盖历史。

### Phase 2: 触发切换——阈值判断

持续监控上下文占用，出现以下任一信号时**主动发起切换**：

| 信号 | 触发值（约） |
|------|------------|
| 上下文占用达到阈值 | 约 80%（估算 token/进度） |
| 对话轮次很长且开始遗忘早期内容 | 模型开始丢失早期决策细节时 |
| 用户明确要求"开新对话/交接/继续" | 任何时候 |
| 完成一个大阶段，自然断点 | 章节/任务完成时 |

### Phase 3: 切换流程——无缝交接

触发切换时，执行以下 5 步：

1. **最终写入**：把当前对话的所有未记录状态补全到 交接.md
2. **校验**：用实际文件/git 状态核对 交接.md 中的"当前状态"是否属实
3. **标记断点**：在 交接.md 顶部写入交接头部（时间、本对话做了什么、下一步）
4. **通知用户**：告知用户"上下文已接近阈值，建议开启新对话，交接已就绪"
5. **新对话引导**：用户开新对话后，新对话按 Phase 0 读取 交接.md 自动继续

**切换的本质**：不是丢失上下文，而是把上下文从 RAM（对话窗口）**完整落盘**到 交接.md，
再由新对话加载。交接.md 是唯一的真相来源（single source of truth）。

## 交接.md 模板

每个对话开始时创建的 交接.md 使用以下结构（可随项目调整，但核心段不变）：

```markdown
# 交接记录

> 本文件是 [项目名] 跨对话的唯一交接入口。每个对话开始先读本文件，结束/切换前更新本文件。

## 交接头部（最新一次切换时更新）
- 上次对话时间：YYYY-MM-DD HH:MM
- 上次对话摘要：一句话（完成了什么）
- 当前阶段：第 N 段对话 / 总体进度 X%

## 项目目标
- 总目标：[一句话]
- 当前子目标：[正在做的一件事]

## 已完成
- [x] 事项（时间/结果）

## 进行中
- [ ] 当前任务
  - 进展：[具体到哪一步]
  - 下一步动作：[下一个具体动作，要可执行]

## 阻塞 / 待决
- 问题描述 / 需要的输入

## 已排除的路径（重要：省得重新推导）
- ❌ 尝试过什么，结果不行，为什么不行

## 重要决策与理由
- 决策：理由

## 关键文件/位置
- 路径 → 用途（让新对话快速定位）

## 时间线
- 追加式记录：时间 + 事件/决策/结果
```

**创建规则**：若项目根没有 交接.md，Phase 0 时按此模板创建。已有则只读+追加，不覆盖。

## 决策启发式（速查）

| 场景 | 怎么做 |
|------|--------|
| 上下文快到阈值 | 主动发起切换（Phase 3），不等被压缩 |
| 完成一个步骤 | 立即追加 交接.md，不攒着 |
| 发现死路 | 记入"已排除的路径"——价值最高，必须写 |
| 状态不确定 | 用 git status / 读实际文件验证，不凭记忆 |
| 新对话开始 | 先读 交接.md，从"下一步"继续 |
| 用户只说"继续" | 读 交接.md 自动继续，不反问 |
| 多对话并存 | 每个对话共享同一个 交接.md（项目级），时间线区分 |

## 诚实边界

- 交接.md 不能恢复**对话中未写下的细节**——所以必须边做边记，不能指望事后回忆
- 模型无法感知精确 token 数，阈值是估算；宁可早切，不可晚切
- 交接.md 需要人工维护时（用户手动编辑），以文件实际内容为准
- 本 skill 解决的是"对话间连续性"，不解决"代码质量/项目设计"本身的问题
- 交接文件本身可能被遗忘更新——Phase 0 的"必读"和 Phase 1 的"必记"是纪律，不是可选项

## 与 Reasonix 集成

- 本 skill 是全局默认 skill：所有新老会话加载全局指令后，长对话会自动按本协议交接
- 交接文件固定名为 `交接.md`，放在**项目根目录**（如 G:\大论文\交接.md）
- 触发词已在 frontmatter 注册；用户说「交接」「新对话」即进入 Phase 3

### 宿主级 hooks 自动化（弥补"无法自动新建对话"的边界）

本 skill 通过 Reasonix 的 hooks 机制（全局 `settings.json`）实现**宿主层自动触发**，不再依赖模型每轮自觉：

| Hook | 触发时机 | 作用 |
|------|---------|------|
| `SessionStart` | 新会话第一次激活 / 清空后 | stdout 注入上下文：强制新对话先读 交接.md，从「进行中/下一步」继续 |
| `PreCompact` | 上下文压缩开始前（约 80% 阈值点） | **自动**向项目根 交接.md 追加兜底记录；stdout 追加压缩指导，提醒压缩前补全交接要点 |
| `Stop` | 每轮对话结束 | 占位（非阻塞、无注入），为未来扩展轮次检测保留 |

**重要边界（诚实说明）**：skill 和 hook 都**不能在宿主 UI 里创建新会话**——"新建对话"仍是用户的界面操作。
但 hooks 已把交接到 80% 阈值时的**触发、记录、提醒、新对话引导**全部自动化，
达到的效果是：用户只需在界面点"新对话"，新对话自动读 交接.md 无缝接力，**中间无需手动作任何交接准备**。
